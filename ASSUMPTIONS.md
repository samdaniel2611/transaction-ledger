# Assumptions & Design Decisions

This document records the assumptions made and the reasoning behind the key design
choices in the Transaction Ledger implementation.

## Identifiers

- Account and transaction `id`s are **UUID v4 strings** stored as the Mongo `_id`. This
  keeps the public API contract independent of MongoDB and makes ids safe to expose and
  pass around in URLs. The models transform `_id` → `id` in their JSON output.

## Balance & money representation

- `balance` and `amount` are stored as JSON/BSON **numbers (doubles)**. This is simplest
  and matches the assessment's integer examples. For a real-world financial system I
  would store minor units as integers (e.g. cents) or use a `Decimal128` type to avoid
  floating-point rounding; this is called out as a known trade-off.
- Initial balance is **always `0`** and generated by the system. Any `balance` sent by
  the client on account creation is ignored by design.

## Transactions

- **Endpoint shape:** transactions are nested under an account —
  `POST /accounts/:accountId/transactions`. This makes the owning account explicit and
  unambiguous (vs. putting `account_id` in the body).
- **Immutability:** the ledger is append-only. There are intentionally **no** update or
  delete endpoints for transactions. Each transaction also stores `balance_after` (the
  account balance immediately after it was applied), which is handy for auditing/history
  display and is never recomputed in place.
- **Duplicate `reference_id`:** treated as **idempotent**. Re-submitting a transaction
  with an existing `reference_id` for the same account creates nothing, changes no
  balance, and returns the existing transaction with `duplicate: true` and HTTP `200`.
  Uniqueness is enforced per account by a **compound unique index** on
  `{ account_id, reference_id }`, so the same `reference_id` can be reused on different
  accounts. A fast-path lookup returns the duplicate before opening a DB transaction;
  the unique index is the race-safe backstop for concurrent submissions.
- **Insufficient-balance debits** are rejected with `409 INSUFFICIENT_BALANCE` and the
  balance is left unchanged.

## Atomicity & consistency

- Creating a transaction and updating the balance is performed inside a **MongoDB
  multi-document transaction** (`session.withTransaction`). If any step throws, the
  whole operation rolls back, so a failed/rejected transaction can never affect the
  balance.
- The balance change itself uses an **atomic conditional update**:
  `findOneAndUpdate({ _id, balance: { $gte: amount } }, { $inc: { balance: -amount } })`
  for debits. Combining the balance check and the decrement into one atomic DB operation
  prevents two concurrent debits from both passing a read-then-write check and
  overdrawing the account.
- **Replica set requirement:** MongoDB multi-document transactions require the server to
  run as a replica set. A `docker-compose.yml` is provided that runs a **single-node
  replica set** and auto-initialises it via the container healthcheck. Alternatives
  (MongoDB Atlas, or a manually `rs.initiate()`-d local `mongod`) are documented in the
  README.

## Money transfer (bonus)

- `POST /transfers` debits the source and credits the destination inside a single Mongo
  transaction. Both accounts must exist and the source must have sufficient balance;
  otherwise the whole transfer rolls back (no partial transfers).
- Two ledger entries are written — a `debit` on the source and a `credit` on the
  destination — sharing the **same `reference_id`** (allowed because `reference_id` is
  only unique *per account*), making the two legs easy to correlate.
- `reference_id` is optional on a transfer; when omitted, a `transfer-<uuid>` reference
  is generated.

## Validation & errors

- Request validation is done with small, dependency-free validators (no external
  validation library) that return `422 VALIDATION_ERROR` with a `details` array of
  `{ field, message }`.
- All errors share one envelope: `{ error: { code, message, details? } }`, with a short
  machine-readable `code` the frontend can branch on, and appropriate HTTP status codes.
- `limit` is capped at **100** to prevent unbounded result sets.

## Pagination & sorting

- History defaults to `page=1`, `limit=20`, sorted **latest-first** by `created_at`
  (ties broken by `_id`). The response includes `page`, `limit`, `page_size`,
  `total_records`, and `total_pages`.

## Scope / out of scope

- **No authentication/authorisation** — out of scope for this assessment; all endpoints
  are open.
- **No automated test suite** is included; the API was verified manually (curl) and the
  frontend end-to-end in the browser. Given more time I would add Jest + supertest
  integration tests (including concurrency tests for the atomic debit path).
- CORS is restricted to the configured frontend origin (`CORS_ORIGIN`, default
  `http://localhost:4200`).
- Currency is assumed to be a single, implicit currency (no multi-currency support).
